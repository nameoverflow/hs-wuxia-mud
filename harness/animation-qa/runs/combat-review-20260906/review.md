# 战斗动画实现评审与重做路线

日期：2026-09-06。仅评审，没有修改产品代码或素材。

## 结论

Verdict: Fail。主观体验评分：35/100。作为正式战斗表现的评审决定：Block。

当前更接近姿势示意器：黄色简化人形、统一跳跃接近、长时间持帧、悬空几何特效、瞬间回位。关键问题既有播放错误，也有表现方向和验收缺口。单独换引擎、增加姿势数量或继续调整骨骼轮廓，不能系统解决问题。

以“成熟的最终体验 + agent 稳定独立生产”为目标，在现有 image_gen 素材约束下，我优先建议采用武侠动态绘本/有限动画演出：完整生成的角色或招式画面、少量有表现力的关键画、镜头编排、独立生成的短促特效、同步音效与结果反馈。其代价是明确选择写意表达，不能承诺连续自然的拳脚运动。

如果连续自然武打是不可妥协的要求，则更值得验证“统一 3D 骨架与动作库 → 离线风格化预渲染 → 2D 运行时合成”。这需要先解决模型、绑定、动作来源，并调整仓库对实际美术必须来自 image_gen 的约束；并非本次已授权或已完成的迁移。不要把支持脚本导出等同于能从零自动创造专业动作。

## 证据范围

- 阅读 action manifest、resolver、PixiFrameActor、PixiBattleStage、game 队列和服务端时长解析。
- `npm run check` 通过：20 个 action、26 个不同角色帧、25 个武学绑定；svelte-check 0 errors、0 warnings。
- 在 Chrome 中挂载实际 `PixiBattleStage.svelte`、实际 resolver 和实际 PNG；固定舞台 640×228。通过隔离 fixture 注入战斗事件，没有改写渲染实现。
- 录制 10.56 秒视频，16 fps 抽样生成四张密集 storyboard，全部检查。
- 直接调用实际 PixiFrameActor 的受控时钟探针也确认：同一 action 第二次 setVisual 后，startedAt 仍为 1000、frame 仍为 punch_strike；设置 hurt 延迟 660ms 后，在 elapsed=0 已显示 hurt。
- 场景：拳击命中、紧接着同招重播、踢击被闪避、敌方剑刺被招架、剑劈命中。
- 这是实际渲染器的合成事件回放，不是完整联网对局；没有评估全设备帧率、移动端、音频播放或所有技能。
- fixture 在若干案例间主动置 idle；连续拳击案例刻意没有中间 idle 渲染，用于模拟连续队列事件。末尾多出的静止时间来自采集等待，不用于评价游戏队列的实际停顿。

临时证据：`harness/tmp/combat-review-20260906/` 中的 `recording.webm`、`timings.json`、`case-*-early.png`、`storyboards/storyboard-001.png` 至 `004.png`。这些是可再生成的执行输出。

## Findings

| Before | After | Why |
| --- | --- | --- |
| [P1] 延迟期间仍采样反应 clip 的第 0 帧 | 反应开始之前保持当前待机；hit/parry/dodge 分别设准备与接触标记 | `pixiFrameActor.ts:52` 将负时间钳成 0，然后立刻切图。受击 clip 第 0 帧就是 hurt；001 第五行已见远处目标后仰，命中还要等到 660ms。 |
| [P1] 相同 action 参数被当成同一次播放 | 资产缓存键与播放实例 ID 分离；每个事件重置播放游标 | `pixiFrameActor.ts:37-38` 没有事件 ID。002 第二行同招再次接近时直接保持 strike。`game.ts:764-774` 在同一回调内先清空再启动下一条，不能依赖组件一定渲染到中间 idle。 |
| [P1] 姿势、位移各自定义时间 | 同一条可 seek 的演出时间线控制姿势、root 位移、接触、反馈和恢复 | `PixiBattleStage.svelte:290` 的前推结束于 delay + action×0.32；拳击是 610.4ms，命中 660ms；剑刺是 546.4ms，命中 700ms。身体已停在近处才换最大姿势。 |
| [P2] 所有近战套跳跃接近，结束直接 set 回位 | 根据招式选踏步、短突进、原地发力；显式设计恢复，或用明确镜头切换结束 | `PixiBattleStage.svelte:281-291`；001 第五行和 003 第三行都是相似小跳。002 第一行第四格可见攻击者跳回远处；003 第四行也有同样断裂。 |
| [P2] 动作语义依赖 2–3 张持帧，构图与 VFX 像调试占位 | 先确定成品美术和镜头，再选择需要的关键画与中间动作；按手、剑尖、接触点布置效果 | `battle-actions.json`、`PixiBattleStage.svelte:357-395,461-477`。003 第一行踢腿轨迹出现在头顶；拳线和招架弧也受固定舞台坐标控制。 |
| [P2] 服务端动作时间与客户端呈现时间不一致 | 区分权威逻辑状态与呈现状态；共享时序契约，积压时压缩恢复或合并低优先反馈 | 服务端 `Entity.hs:171-180` 取 manifest duration；resolver 又增加 380–420ms。`game.ts:657-670` 的 HP 快照立即更新，动画却排队；存在血条领先于当前演出的结构性风险，本次没有联网量化积压。 |
| [P2] 校验通过和角色帧预览被当作最终体验的证据 | 校验之外强制回放完整双方交手、连续事件和不同结果分支 | `validate-animation-data.mjs` 检查字段、时长和路径；`render-frame-preview.mjs` 只拼角色帧，不执行舞台位移、VFX、目标反应与队列。 |

重要的时长实例：当前拳击为 380ms 接近 + 720ms 动作 = 1100ms；命中点为 380 + 280 = 660ms。首个姿势其实从事件开始就已出现，因此起手画面持续约 660ms，然后 strike 持续约 440ms。剑刺为 900ms，命中 700ms；踢击为 1260ms，命中 760ms。问题是阶段分配及动作对应关系，不是简单把整段统一加速。

舞台实现中没有发现接入命中音效或真正暂停整套演出时钟的 hit stop。增加这两项有帮助，但不能弥补动作语义和接触位置错误。UI 动画 skill 的 300ms 等规则不机械应用于武打表演。

## 路线比较

下表是工程判断，不是对这些路线做过同成本成品基准测试。

| 路线 | 最终体验潜力 | Agent 自主生产 | 主要限制 |
| --- | --- | --- | --- |
| 完整立绘/关键画 + 动态绘本式镜头演出 | 成品感、武侠气质、绝招表现强 | 在锁定模板后相对高 | 写意与剪辑表达，不等于连续自然武打 |
| 统一 3D rig/动作库 + 2D 离线预渲染 | 连续动作、转身、重心、武器关联更有保障 | 基础资产成立后较高，前置条件重 | 模型与动作来源、重定向、脚滑、穿插、风格化；新动作仍可能需要调优 |
| Spine 等成熟 2D 骨骼工具 | 熟练制作时可很高 | 导出自动化高，从零美术与绑定自动化不确定 | 分件、权重、透视换图、关节与衣物修补；有 CLI 不代表全流程无人干预 |
| AI 逐帧生成完整 sprite 动画 | 单帧美术可能很好 | 连续动作批量验收不稳定 | 身份、比例、接触、武器、收招与帧间变化需要反复筛选 |
| AI 视频直接作为交手动画 | 单段演出可能出彩 | 不适合作为普通战斗核心的首选 | 命中/闪避分支、目标复用、精确打断和同步都需要额外解决 |

不建议继续自研一套从分件、mesh 到动作编辑的 2D 动画软件。成熟引擎能节省基础设施工作，但不会自动提供动画设计能力。

## 推荐的重做边界

保留 Haskell 战斗事实、WebSocket 事件、action ID 与 YAML 绑定。Pixi 的纹理合成与舞台也可以保留；没有证据证明必须换渲染引擎。

重做三块：

1. **表现契约**：以一次出招或一次交锋为制作单位，不以“生成两张人物图”为单位。定义准备、发力、接触、反应、恢复、文字和音效的时机。
2. **演出运行时**：事件有独立实例 ID；单一播放时钟；支持 pause/seek/replay；镜头、姿势、位移、VFX、音频和飘字共享标记。将人物身体、拳头、脚、武器尖端等锚点与舞台坐标分开。
3. **生产与验收工具**：让 agent 修改数据、生成候选和看真实回放；新增普通招式不应反复改舞台组件的条件分支。

以动态绘本路线为例：idle 保持稳定对峙；出招时短暂强调攻击者及招式方向；用有力的完整关键画完成挥击；接触瞬间同步目标反馈、局部生成 VFX、音效和短停顿；随后明确恢复到对峙构图。普通招式保持克制，绝招才使用较强镜头切换，避免每击都播放大片。

如果转向 3D，推荐先用固定正交相机离线输出透明角色序列，保留目标、特效和数字的实时合成；不要把双方及战斗结果烘焙成一整段视频。这样可以复用同一个攻击 clip 来处理命中、闪避和招架，并继续使用现有 2D 客户端。资产数量随角色×动作×方向增长是这条路线的现实成本。

## 无人干预能力的验收方式

不要只统计 agent 能生成多少张图，应统计每个合格动作需要多少次生成、多少时间/成本、多少人工介入，以及批量新增动作后的回归率。

建议闭环：动作说明 → 从已验收的动作/演出模板选择 → 参数或素材候选 → 机械格式处理 → 完整舞台回放 → 硬规则与视觉判定 → 有界重试 → 版本化发布。

- 硬规则覆盖重复播放、事件仅触发一次、姿势不能提前受击、无裁切、锚点稳定、资源预算、首尾恢复、队列和结算顺序。
- 视觉检查覆盖动作是否读得懂、力量来自哪里、接触是否可信、人物是否漂移、镜头是否抢文字、与锁定风格是否一致。视觉分数是主观证据，不能冒充确定性测试。
- 预设正反参考样例，隔离生成与评审提示，保留不通过原因；全速、慢放、密集 storyboard 和多次连续播放各解决不同问题。
- 自动重试设上限；失败则保留已通过版本或使用批准过的通用招式。若要求零人工介入，系统必须允许“这条新动画没有产出”，不能用降低标准来换取每次都成功。
- “模板内新增招式”与“首次创造一个全新武术动作”是两种自动化难度，应分别报告。

## 先做的可否决实验

先实现一段约 10 秒、能够反复回放的完整交锋：普通拳击命中、同招连续重播、剑招被挡、踢击被闪避、最终一击与结算。固定角色和同一画面预算。

动态绘本路线先建立一个成品基准；若连续武打是核心需求，则改用同一组事件验证 3D 预渲染路线，不同时铺开两套生产系统。第一套交锋未达到体验标准前，不批量做武功素材。

验收至少包括：正常速度动作语义清楚；没有提前反应和瞬移式恢复；连续重播正确；手机尺寸可读；减弱动态模式仍保留结果；后续数个模板内招式无需人工改图/拖关键帧即可过关。不能把一次成功当成整个生产系统已经稳定。
