# 战斗动画表现设计指南

本文记录战斗动画的高层设计方法。它不绑定某个武功、某个招式或某一套素材，而是给以后设计、评审和调试战斗动画时使用的共同判断标准。

目标不是把 MUD 做成完整格斗游戏，也不是追求大量逐帧角色动画。目标是用少量关键姿势、清晰的时间节奏、短促的位移和多层反馈，让文字战斗看起来有武侠感、有打击感、可读、可扩展。

相关系统架构、协议和 catalog 实现见 [半回合制战斗动画系统](./battle-animation.md)。本文只讨论动画表现原则。

## 当前实现约定（2026-09）

当前采用简化剪影交锋小舞台。完整的实现和命令见 [战斗动画系统](./battle-animation.md)。角色采用 SVG 圆头小人与圆润肢体轮廓并连续插值；镜头克制，围绕近距离交手组织姿势、接触、收势。runtime 使用 BattleClock 与纯函数 battleDirector；命中、显示气血和声音共享时刻。下文时长区间属于设计参考，以 action manifest v4 的实际时间标记为准。

## 核心判断

一段好的轻量战斗动画不是“每一帧都有新角色画”。它通常由下面几件事共同成立：

- 角色姿势少，但姿势语义清楚。
- 大部分时间让画面稳定，玩家能读状态和文字。
- 出手瞬间有强烈的速度反差。
- 命中帧足够密：位移、轨迹、闪光、受击、飘字同时发生。
- 特效短促，不长期粘在武器或角色上。
- 动作之间有停顿，让半回合战斗像“出招 - 结果 - 读文字 - 下一招”。

如果只让角色匀速滑动，即使帧率很高，也会显得轻、漂、没有劲。反过来，如果关键帧很少，但时序、速度曲线和命中反馈正确，画面会自然很多。

## 动画的五层

设计任何战斗动画时，先拆成五层，而不是直接问“这个招式要画多少帧”。

### 1. 姿势层

姿势层解决“这是什么动作”。它是语义，不负责完整流畅度。

常见姿势类型：

- idle：待机、站定、蓄势。
- windup：出手前的压低、后撤、抬手、转身。
- strike：动作最大伸展或最有辨识度的一帧。
- recover：回到待机或收招，很多情况下可以复用 idle。
- hurt：受击后仰、弯腰、偏移。
- dodge/parry：闪避、招架、格挡的通用反馈。

原则：

- 每个姿势必须在静止截图里能读出大概含义。
- 不要为了“流畅”堆很多相似中间姿势；中间过渡优先交给位移、缩放、透明度和特效。
- 姿势必须有统一 foot anchor。角色移动时脚底锚点要稳定，否则会像贴图在飘。
- 攻击姿势不一定要多，但 silhouette 轮廓要差异明显。刺、扫、挑、掌、腿、暗器这类大类要能一眼区分。

### 2. 运动层

运动层解决“它怎么动”。轻量战斗动画的自然感主要来自这里。

常用运动原语：

- hold：短暂停住，让玩家读动作开始或结果。
- windup lean：轻微反方向准备，例如后撤、下沉、转肩。
- dash/lunge：极短时间内接近目标。
- overshoot：命中后略过目标一点点，再回收。
- recoil：目标被打退、后仰或抖动。
- return：双方回到自己的锚点。

运动原则：

- 不要匀速。出手应先慢后快，命中后快速停住或轻微回弹。
- dash 时间通常比想象中短，80-140ms 就足够表达爆发。
- windup 可以很短，但不能没有。没有准备动作的攻击容易像瞬移或滑动。
- 命中后不要立刻回 idle，保留 80-180ms 让玩家看清结果。
- recover 可以长一点，因为它承担“读文字”和“让队列喘气”的作用。

推荐基础时间结构：

```text
pre-hold:       120-300ms，可选，用于读起手和日志
windup:          80-160ms，轻微蓄势
strike:          80-140ms，爆发接近或发力
impact hold:    100-180ms，命中、特效和飘字峰值
recover:        220-420ms，收招、回位、读结果
between events: 300-900ms，按队列和日志节奏调整
```

这个结构不是固定模板。不同招式可以变，但“稳定 - 爆发 - 命中密集 - 停顿”这个节奏不要丢。

### 3. 特效层

特效层解决“力从哪里来、打到了哪里”。在少关键帧方案里，特效比角色中间帧更重要。

常见特效：

- 攻击轨迹：红线、白弧、墨痕、剑气、掌风。
- 命中火花：小范围闪光、裂纹、血点、冲击环。
- 防守反馈：蓝色招架弧、闪避残影、护体光。
- 屏幕/舞台反馈：轻微震动、暗闪、短暂停帧。
- 残影：快速位移后留下淡影。

特效原则：

- 特效要短。攻击轨迹通常只应该在命中附近峰值出现 2-8 帧。
- 轨迹不要长期粘在武器上，否则会像“武器变长”，不是“挥出一击”。
- 轨迹方向要和动作语义一致。直线更像刺、点、射；弧线更像扫、劈、格挡；竖向弧更像挑、劈落。
- 特效颜色要有语义。红/橙偏攻击和伤害，蓝/白偏招架和防守，灰/白残影偏闪避。
- 同一次命中可以叠 2-3 个轻量特效，但不要让特效互相抢读。优先级是：动作方向 > 命中点 > 伤害结果。

### 4. 结果层

结果层解决“发生了什么战斗事实”。它必须和 server 结果一致。

常见结果表现：

- hit：目标 recoil + hit spark + damage number。
- dodge：目标横移/残影 + miss/闪避字样。
- parry：防守弧 + 轻微震动 + 架/格挡字样。
- heal：上浮绿色数字或柔和亮光。
- effect tick：不打断主动作的小飘字。
- settlement：最后一击后再显示胜负，不要提前抢走命中反馈。

原则：

- 飘字必须和命中帧同步，不要在攻击还没到时提前出现。
- 飘字要保持足够久，通常 250-500ms。
- 飘字可以稍微漂移，但不要大幅飞走；文字游戏里可读性优先。
- 受击反馈要比攻击轨迹更靠近目标身体，否则玩家看不出打中了谁。
- miss、dodge、parry 不能只是伤害数字为 0；它们要有不同姿态或特效。

### 5. 文本节奏层

MUD 战斗不是纯动画，它同时是文字叙事。动画必须服务文字节奏。

原则：

- 战斗日志不要一次性刷完，让每个 half-turn 开始时才追加对应文本。
- 长文本更新可以放在 recover 或 between events 阶段，让玩家有时间读。
- 动画不需要全程运动。停顿是文字战斗的组成部分，不是缺陷。
- 连续技可以缩短停顿，但仍要保留每次命中的可读峰值。
- 队列积压时可以压缩 recover，但不能丢失结果反馈。

## 少关键帧设计方法

设计新动画时，用下面顺序思考：

1. 这次动作的语义是什么：刺、扫、挑、劈、掌、指、腿、暗器、内力、身法？
2. 最少需要哪几个姿势能读出这个语义？
3. 出手前有没有反方向准备？
4. 命中点在哪里？
5. 哪个特效最能表达方向和力量？
6. 结果是什么：hit、dodge、parry、heal、tick？
7. 文本什么时候出现，什么时候读？
8. recover 后画面是否干净？

如果一个动作看起来不自然，优先调整下面四件事：

- timing：是不是匀速、太慢、太拖？
- impact density：命中帧是不是太空？
- effect lifetime：轨迹是不是出现太早、停留太久？
- target feedback：目标是不是反应太弱？

不要第一反应就增加角色帧数。更多帧可能让动作更平滑，但不一定让它更有力。

## 基础时间线模型

大多数出手动画可以从下面的抽象时间线开始：

```text
0%    idle/hold，双方站定
15%   windup，攻击者轻微反向蓄势
30%   launch，攻击者开始快速位移
45%   impact，攻击姿势最大、轨迹峰值、目标反馈、飘字出现
58%   settle，攻击者略回收，目标仍处于反馈
75%   recover，特效淡出，文本可读
100%  idle，准备下一条队列事件
```

可以按动作性质变形：

- 快刺：缩短 windup 和 strike，总时长 550-750ms。
- 重击：加长 windup 和 impact hold，总时长 850-1200ms。
- 闪避：目标先动，攻击轨迹落空，miss 文本在目标偏移后出现。
- 招架：双方距离变化小，防守弧和 hit pause 更重要。
- 内功/远程：攻击者位移少，projectile 或 wave 的时间线更重要。

## 例子：短促直击

这不是固定招式，只是直线攻击的设计示例。

```text
0-120ms    hold：双方站定，日志准备显示
120-220ms  windup：攻击者后脚压低、身体轻微后撤
220-330ms  strike：攻击者快速前压到目标前
300-380ms  trail：直线轨迹出现并快速变亮
330ms      impact：目标后仰，火花和伤害数字出现
380-520ms  impact hold：目标反馈保持，轨迹淡出
520-760ms  recover：攻击者回位或收招，伤害数字上浮淡出
```

关键点：

- 轨迹不是从 120ms 一直挂到 760ms，而是在命中附近短暂出现。
- 攻击者的最大位移在很短窗口里完成。
- 伤害数字不提前出现。

## 例子：横向扫击

横向扫击不一定需要更多角色帧。它需要更明确的弧线和目标反馈。

```text
0-160ms    windup：攻击者略转身或后撤
160-300ms  strike：攻击者前压，白/红弧线从后向前扫过
260-360ms  impact：弧线经过目标身体，目标侧向 recoil
360-520ms  settle：弧线残影淡出
520-850ms  recover：双方回到站位
```

关键点：

- 弧线是主读形，角色姿势只是辅助。
- 横扫命中时目标最好有侧向偏移，而不只是后仰。

## 例子：招架/格挡

招架的重点不是攻击者位移，而是“攻击被挡住”的瞬间。

```text
0-140ms    攻击者起手
140-260ms  攻击轨迹接近目标
250ms      防守弧出现，目标不退或只小幅后震
250-330ms  hit pause：双方短暂停住
330-520ms  蓝/白弧线淡出，显示“架”或“格挡”
520-760ms  recover
```

关键点：

- 防守者要稳，不能像被打飞。
- 蓝白弧线和短暂停帧比大位移更重要。

## 例子：闪避

闪避要让玩家看出“攻击经过了原位置，但目标已经不在那里”。

```text
0-160ms    攻击者起手
160-260ms  目标先小幅偏移或留下残影
240-340ms  攻击轨迹穿过目标原位置
300ms      显示“闪”或 miss 文本
340-620ms  残影淡出，目标回到站位或停在新位置
```

关键点：

- 闪避反馈要早于或同步于攻击经过，不能等攻击结束才消失。
- 残影和 miss 文本比伤害数字更重要。

## 常见问题与修法

### 看起来像滑动

症状：

- 攻击者从 A 匀速移动到 B。
- 没有明显起手和命中峰值。

修法：

- 缩短 strike 时间。
- 加一个 80-160ms 的 windup。
- 使用 ease-in 后 sudden stop，或自定义 snap 曲线。
- 在命中帧加 hit spark、短暂停顿和目标 recoil。

### 看起来没有打击感

症状：

- 命中发生了，但画面不疼。
- 伤害数字出现，目标没明显反馈。

修法：

- 目标后仰/侧移距离加大一点。
- 命中点加短闪或小火花。
- 伤害数字在命中帧出现，并保持 250ms 以上。
- 可以加 40-80ms hit pause，但不要滥用。

### 特效像贴在武器上

症状：

- 红线或弧线从出手开始一直存在。
- 轨迹不随命中时机变化。

修法：

- 让特效 start 接近 impact。
- 缩短 duration。
- 峰值只保留 2-8 帧。
- 淡出时轻微漂移或扩散。

### 动画太乱

症状：

- 同一帧有太多光效、数字、文本。
- 看不清谁打谁。

修法：

- 明确主层级：角色 > 攻击方向 > 命中点 > 数字。
- 降低非关键特效透明度。
- 同一事件最多让一个主轨迹和一个命中特效抢视线。
- 保证飘字不压住角色关键轮廓。

### 动画太慢

症状：

- 每次攻击拖到一秒多，但只是普通攻击。
- 队列堆积，日志和动作脱节。

修法：

- 普通攻击控制在 600-850ms。
- 主动技能才使用 850-1300ms。
- 队列积压时压缩 recover。
- 文本可以继续保留，但动作不要等文本读完才结束。

## 与系统设计的关系

本文的原则应落到 [resources/scripts/combat_actions/](../resources/scripts/combat_actions/)、[client/src/battle/battleActionCatalog.ts](../client/src/battle/battleActionCatalog.ts) 和 [client/src/battle/animationResolver.ts](../client/src/battle/animationResolver.ts)，而不是散落在组件 if/else 里。

推荐把每个动作拆成：

- actorClip：攻击者姿势。
- targetReaction：不同结果的反馈姿势。
- motion：位移原语。
- vfx：攻击轨迹、命中特效、防守特效。
- floatText：伤害、治疗、miss。
- textTiming：日志何时进入消息区。

server 提供战斗事实和 animation hint。client 根据 catalog 选择表现，战斗结果以 server 事件为准。

当前 `SilhouetteBattleStage.svelte` 只消费 `ResolvedBattleTimeline`。新增动作时优先改武学 YAML 的固定 `animation.action`、action manifest 和 SVG pose；只有新增通用渲染 primitive 时才改舞台组件。

## 设计检查表

设计或评审一段动画时，逐条检查：

- 静止姿势是否能读出动作大类？
- 角色 foot anchor 是否稳定？
- 出手是否避免匀速滑动？
- 是否有短 windup？
- 命中帧是否足够密？
- 轨迹是否在命中附近出现，而不是全程挂着？
- 目标反馈是否明显且符合 hit/dodge/parry？
- 飘字是否同步、清楚、不过度遮挡？
- recover 后画面是否干净？
- 普通攻击是否足够短？
- 队列连续播放时是否有文字可读停顿？
- 这个动作是否由 YAML `animation.action` 固定绑定，并由 catalog/manifest 复用，而不是写死到组件？

## QA 建议

视觉 QA 时不要只看单帧截图。使用项目内 `$animation-visual-qa` 流程：

1. 录制完整动画。
2. 生成高密度 storyboard。
3. 先看全局节奏，再看舞台裁剪。
4. 判断是否符合本文的时间、命中密度和可读性原则。
5. 如果要改，优先改 timing、特效生命周期和目标反馈。

主观评审时可以直接问：

```text
这段动画是否读得出动作语义？
是否有起手、爆发、命中、恢复？
哪里像滑动？
哪里缺打击感？
特效是否出现太早或停留太久？
目标反馈是否足够明显？
```

这些问题比“帧率够不够”更适合当前项目阶段。
